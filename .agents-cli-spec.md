# Panergos Agent Specification

> **Roadmap, not a release claim.** This document describes the intended end state. As of Durable Missions 0.1.0, Capability Forge, Policy Ledger, Evidence Gates, and comparative benchmarks remain planned. See [PANERGOS.md](PANERGOS.md) for implemented status.

## Overview

Panergos Agent is a public, local-first, model-agnostic autonomous agent runtime. Its name combines *pan* (“all”) and Greek *ergon* (“work”). Legal provenance and licensing terms are recorded only in the repository `NOTICE` and `LICENSE` files.

The runtime provides CLI/TUI/desktop/API/library entry points; provider routing and fallbacks; tools, skills, memory, plugins, MCP, browser, voice, vision, scheduled work, messaging gateways, checkpoints, batch trajectories, and subagent delegation.

Panergos differentiates through four additions:

1. **Durable Missions** — persistent multi-session agent teams with typed shared state, live peer messaging, budgets, leases, recovery, and auditable handoffs.
2. **Capability Forge** — when a request is outside installed capabilities, create the smallest isolated capability pack or one-off artifact, test it, disclose permissions and dependencies, and install only after approval.
3. **Policy Ledger** — deterministic, capability-based authorization outside the model, with approval-sensitive actions, secret isolation, provenance, and attributable side effects.
4. **Evidence Gates** — replayable traces and required deterministic/evaluated quality gates before capabilities or releases are promoted.

"No limits" means no fixed task taxonomy and no single-provider lock-in. It does not mean unlimited permissions, spend, runtime, or unsafe autonomy.

## Example Use Cases

- "Build a web application for this idea." The agent creates a durable mission, delegates research/design/build/review tasks, produces the repository, runs checks, and returns artifacts plus evidence.
- "Research this unfamiliar field and publish a cited report." The agent plans, searches, critiques, verifies sources, and produces a report with traceable citations.
- "Connect to an API you have never seen." Capability Forge studies the API, generates a quarantined capability pack, validates schemas and permissions, runs tests, and asks before installation.
- "Run this every Monday and send it to my team." The scheduler invokes the same durable engine with idempotency, pre-granted scopes, and delivery evidence.
- "Continue the work next week." Mission state, child-agent state, artifacts, approvals, budgets, and handoffs resume from the event ledger rather than a probabilistic summary.
- "Use another model or a local model." Existing provider routing remains available, with per-task policy and fallback.
- "Ask for something unrelated to the original agent." The runtime either uses an existing tool/skill/MCP capability, creates the requested one-off artifact, or safely forges a reusable capability pack.

## Architecture & Sub-Agents

### Shared runtime foundation

- `AIAgent` remains the shared execution core for CLI, gateway, ACP, batch, API, desktop, and Python callers.
- Existing provider resolution, tool registry, plugin system, skills, memory, terminal backends, MCP, gateway adapters, cron, and session storage remain compatible.
- Compatibility-sensitive changes stay isolated and tested to reduce regression risk.

### Durable Missions

This section is the target end state. Durable Missions 0.1 does not yet enforce mission budgets; its lifecycle policy covers the `panergos_mission` interface but not inherited raw Kanban callers, and operating-system process shutdown remains a staged action protected by durable stop fences and quarantine rather than one SQLite transaction.

A mission is an append-only, SQLite-backed coordination unit:

`planned -> running -> waiting_approval -> succeeded | failed | cancelled`

A mission owns:

- goal and measurable acceptance criteria;
- parent/child task graph;
- persistent specialist profiles and isolated context;
- typed shared facts and artifact references;
- inbox/outbox messages with delivery status;
- tool, token, cost, wall-time, and concurrency budgets;
- leases and idempotency keys for resumable work;
- approval requests and decisions;
- immutable event history plus materialized status.

The coordinator creates only roles required by the task. Specialists communicate through messages, typed results, and artifacts rather than copying entire transcripts. A crashed worker can resume from its last committed action boundary.

### Capability Forge

Capability resolution follows this ladder:

1. native tool or existing project helper;
2. installed skill/plugin/MCP server;
3. one-off artifact created in an isolated workspace;
4. quarantined reusable capability pack.

A reusable pack declares its command/protocol, schemas, permissions, secrets, network destinations, dependencies, tests, and version. Generated code runs outside the trusted core. Installation requires passing conformance checks and a human approval that shows the exact diff and permission request. Promotion to a public registry is a separate reviewed process.

### Policy Ledger

Every tool or extension declares:

- read/write filesystem roots;
- network destinations;
- secret handles;
- side-effect class;
- timeout and resource budget;
- idempotency behavior;
- whether explicit approval is required.

The model cannot grant itself permissions or approve its own action. Headless jobs fail closed when authority is missing. Untrusted web/document content is data, never policy.

### Evidence Gates

Each run records provider/model metadata, prompt lineage, tool calls/results, approvals, artifacts, latency, tokens, cost, errors, retries, state transitions, and final outcome. Deterministic artifact checks are preferred; LLM judges are limited to qualities that cannot be checked mechanically.

## Tools Required

All existing Panergos tools and integrations remain in scope. Panergos additions use:

- **SQLite/WAL/FTS5** — durable missions, messages, state, events, and searchable memory; no new database dependency.
- **Existing terminal backends** — isolated task and capability execution.
- **Existing tool registry and plugin hooks** — mission and capability integration without a second tool framework.
- **Git/GitHub** — source control, public releases, CI, issues, and contribution flow; authenticated by the operator.
- **MCP/ACP/A2A** — external tool, IDE, and agent interoperability where already supported or added behind versioned adapters.
- **Existing provider adapters** — model access; credentials remain in the existing credential system and never enter prompts.
- **Optional container runtime** — whole-process isolation for untrusted inputs and capability packs.

## Data Sources & Authentication

- Provider credentials use the existing Panergos credential/OAuth mechanisms.
- User-specific secrets are passed by handle at execution time, scoped to the tool and never persisted in prompts, traces, capability source, or generic child-process environments.
- Web, browser, MCP, messaging, and external API access remains opt-in and attributable.
- Local-only mode produces no undeclared egress.
- Each tenant/profile has separate missions, storage, workspaces, grants, secrets, and worker identity.

## Constraints & Safety Rules

- Preserve all copyright and permission notices required by the repository `NOTICE` and `LICENSE` files.
- Panergos uses distinct naming and identity; legal attribution remains in those legal files.
- Never claim universal capability or superiority without a published benchmark against a pinned Panergos release.
- The model cannot expand its own authority.
- Sending, publishing, purchasing, deleting, credential changes, permission escalation, and irreversible/high-value actions remain approval-sensitive unless explicitly pre-granted for a bounded headless job.
- Generated or third-party code is untrusted until isolated, scanned, tested, and approved.
- Retrieved content cannot silently become system policy, durable memory, or an installed capability.
- Filesystem access uses canonical, symlink-safe paths and allowed roots.
- Network access blocks private/link-local metadata targets unless explicitly allowed and defends against DNS rebinding.
- Every run has bounded turns, tokens, time, cost, concurrency, and cancellability.
- Checkpoints and rollback protect material workspace mutations.
- Self-improvement may change reviewable skills, memories, routing hints, and capability packs; it may not silently rewrite the security kernel.
- Telemetry is local by default and external export is opt-in.
- Accessibility basics and secret/error handling are not optional.

## Success Criteria

Each comparison target must be a pinned, publicly available release run with the same model, task environment, credentials, limits, and number of trials.

A release candidate must meet all of these:

1. Preserve upstream smoke/eval compatibility for critical CLI, API, gateway, provider, tool, memory, skill, MCP, browser, scheduler, and delegation paths.
2. Resume at least 99% of forced interruptions injected after committed action boundaries without duplicate external side effects.
3. Pass durable multi-session tests covering peer messaging, typed shared state, isolated profiles, cancellation, leases, budgets, and restart recovery.
4. Produce no unapproved destructive action or secret-exfiltration escape in the published adversarial suite.
5. Attribute every external side effect to a run, actor, tool, capability grant, and approval or pre-grant.
6. Complete at least 70% of held-out unfamiliar API/tool tasks through Capability Forge, then reuse the generated pack successfully in a clean later session.
7. Require no core edit for a third party to create and pass a capability-pack conformance test.
8. Keep local-only test egress at zero except explicitly mocked/allowed endpoints.
9. Enforce deterministic relevant-change CI gates and behavioral eval gates before merge.
10. Publish benchmark inputs, pinned commits, transcripts, graders, failures, cost/latency data, and confidence intervals.
11. Claim "better" only when paired pass@1 is at least 10 percentage points higher with a 95% confidence interval above zero, critical-domain capability is non-inferior within 2 points, and median cost per successful task is at least 20% lower without reducing success.
12. Provide clean documented installation on Windows, macOS, Linux/WSL, and Docker.

## Evaluation Plan

- Unit/integration tests cover deterministic state, policy, recovery, schema, permission, and compatibility behavior.
- Behavioral evals cover coding, terminal work, research/citations, data analysis, document/media artifacts, browser tasks, scheduling, messaging, MCP, multi-agent coordination, prompt injection, capability gaps, and crash recovery.
- Forced-failure tests kill workers before/after tool calls and verify leases, idempotency, and replay.
- Security tests cover path traversal, symlinks, SSRF/DNS rebinding, prompt injection, poisoned memory/skills, malicious MCP/capability packs, secret leakage, approval bypass, and cross-user isolation.
- Benchmarks use deterministic artifact graders whenever possible and repeat stochastic cases.

## Assumptions

- The user delegated project naming; the chosen public identity is **Panergos Agent** and repository slug is `panergos-agent`.
- Existing functionality is retained only when it passes Panergos compatibility and security checks.
- Licensing and provenance are governed by the repository `LICENSE` and `NOTICE` files.
- The product is model/provider agnostic and preserves local-model support.
- GitHub Actions is the default CI; cloud deployment is not performed without a separate explicit deployment decision.
- Local-first single-node operation remains the default; distributed infrastructure is added only where measured concurrency or tenant isolation requires it.
- Broad scope is intentional. Delivery is phased so each phase is testable and releasable, but the end-state includes all sections above.
